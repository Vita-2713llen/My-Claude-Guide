# Інструменти прогону: однаково на будь-якій машині

**Навіщо.** Два прогони попередньої версії скіла на одному сайті дали різні списки багів: кожен
писав власний код вимірювання й сам вирішував, які рядки чекліста виконати. Тепер вимірює **код
скіла** з `scripts/`, а агент запускає інструменти, читає манифест, дивиться скріншоти й закриває
лише те, що потребує очей або рішення людини.

**Правило:** заборонено писати власні скрипти для того, що робить інструмент. Якщо інструмент
чогось не вміє — доповнюється **інструмент** (`scripts/`), новий ID у `registry.cjs`, потім
`node <skill>/scripts/registry-md.cjs`. Лише тоді звітуй.

## Встановлення

Один раз на машину — за `INSTALL.md` (macOS / Windows / Linux, `npm ci`, `npm run browsers`,
перевірка `npm test`). Глобальних пакетів і `sudo` агент не ставить; кроки з `sudo`, паролем чи
GUI (Linux `browsers-deps`, Xcode, Safari Remote Automation) робить людина.

## Де запускати — однаково на будь-якій машині

**Робоча тека — тека проєкту**: там лежать `.qa-state.json`, `qa-target.json`, `qa-out/` і
`.qa-snapshots/`. Усі команди запускаються з неї, а скрипти викликаються **за повним шляхом теки
скіла** (`<skill>` — тека, де лежить `SKILL.md`; Claude Code показує її як base directory скіла).
Ніколи не роби `cd` у теку скіла для прогону: інструменти самі відмовляються писати результати
всередину скіла. Копій скриптів у теці проєкту немає — якщо там лежить стара копія, вона не
використовується.

- macOS / Linux (bash, zsh): `S="$HOME/.claude/skills/qa-check/scripts"` → `node "$S/qa-run.cjs" --out qa-out`
- Windows, Git Bash (це оболонка інструмента Bash у Claude Code на Windows):
  `S="$(cygpath -m "$HOME/.claude/skills/qa-check/scripts")"` → `node "$S/qa-run.cjs" --out qa-out`.
  `cygpath -m` дає шлях виду `C:/Users/…`, який Node читає з `MSYS_NO_PATHCONV=1` і без нього.
- Windows PowerShell: `$S="$HOME\.claude\skills\qa-check\scripts"` → `node "$S\qa-run.cjs" --out qa-out`

Якщо скіл встановлено не в `~/.claude/skills/qa-check` (тека проєкту `.claude/skills/`, інша
тека користувача), `S` — це `<base directory скіла>/scripts`, як його показав Claude Code.

**Одна тека `qa-out/` на проєкт.** Крок 1 (`snapshot.cjs`) відкриває новий прогін: усе, що лишив
попередній, переїжджає в `qa-out/_prev/<runId>/` (нічого не видаляється), і пишеться
`qa-out/run.json`. Манифест зливає **лише результати цього прогону**; файли інших прогонів чи
іншого сайту він показує як «ignored». Не копіюй результати з іншої машини в `qa-out/` руками —
для цього є `record.cjs --import` і `--as <мітка>`.

**Частковий перезапуск** (`--pages`, `--engines`, `--widths`, `--quick`) — лише в окрему теку
(`--out qa-out-recheck`). Його манифест позначений як частковий і в звіт чи handoff не йде.

## Порядок прогону — завжди цей, завжди повністю

| Крок | Команда (з теки проєкту) | Закриває |

| 1 | `node "$S/snapshot.cjs" --out qa-out` | RUN-01: відбиток сайту, що змінилось з минулого прогону |
| 2 | `node "$S/qa-run.cjs" --out qa-out` (+ `--form-errors` **лише з явного дозволу людини в цьому прогоні**: порожня відправка форм) | 160 ID: присутність, сторінки, платформа, доступ, умови прогону, лінки, тогли розгорнутими, слайдери, ховери, бургер, модалки, форми, верстка, контент, SEO, кросбраузер (WebKit, Firefox, Edge) |
| 3 | `node "$S/spell.cjs" --out qa-out` → прочитати `spell-candidates.json` і `grammar-candidates.json` у контексті, записати висновок (`record.cjs`) | TEXT-02, TEXT-08 |
| 4 | `node "$S/lighthouse.cjs" --out qa-out` — **завжди, на кожному прогоні стадій 2 і 3** (на стадії 1 — ні: PERF-01 там ⊘), лише коли на машині не запущений жоден інший інструмент чи браузерний прохід (скрипт сам іде послідовно й сам відмовляється стартувати поруч з іншим) | PERF-01 |
| 5 | `node "$S/safari-real.cjs" --out qa-out` — **на будь-якій ОС** (поза macOS сам пише NOT RUN з маршрутом) | XB-02; додаткові докази FORM-07, FORM-10 |
| 6 | `node "$S/ios.cjs" --out qa-out` — **на будь-якій ОС** (поза macOS / без Xcode сам пише NOT RUN з маршрутом) | XB-03, LAY-09; доказ FORM-11 |
| 7 | аудит адмінки платформи за RUN-05 (нижче); стадія 1 — не запускається | WordPress: WP-01…12, WP-14, FORM-08/09, CMS-02; Webflow: WF-01, -04, -05, -06, -09, -10, -11 |
| 8 | рядки людини й рядки без скрипта → `node "$S/record.cjs" --out qa-out --id … --status …` | `person`, `route`, `webflow` |
| 9 | `node "$S/manifest.cjs" --out qa-out`, потім `node "$S/state.cjs" --out qa-out` | `qa-out/manifest.{md,json}`: **кожен ID** з одним статусом і доказом; прогін і статуси в `.qa-state.json` |
| 10 | звіт у чат — **лише з `qa-out/manifest.json`**; режим 4: `node "$S/handoff.cjs" --out qa-out --project "<назва>"` пише файл handoff (розділи 2–5 з манифесту), агент дописує лише обсяг та інтерв'ю (`references/reports.md`) | — |

**Стадія 1 (локальна збірка HTML):** ті самі кроки з `--local <тека збірки>` для `snapshot`,
`qa-run`, `safari-real` і `ios` (інструмент сам піднімає сервер на 127.0.0.1 — порт виводиться з
шляху теки, тож усі інструменти бачать той самий origin — і вимикає його після прогону; `file://`
не використовується ніколи). `spell`, `record` і `manifest` — без змін (стадію манифест бере з
результатів `qa-run`). Крок 4 (Lighthouse) і крок 7 (адмінка) на стадії 1 не запускаються. Рядки,
що існують лише на задеплоєному сайті (HSTS, sitemap, листи форм, адмінка, швидкість…), манифест
сам ставить ⊘ із причиною «стадія 2».

**Режими 2 і 3** запускають ті самі команди з тими самими прапорами. `--full` (без шаблонної
вибірки) у протокольних прогонах не використовується: вибірка детермінована, вміст і так
перевіряється на кожній сторінці. Якщо дизайнер явно просить `--full`, прапор записується в RUN-07,
і такий манифест порівнюється лише з іншим `--full`.

**Тривалість, фон, падіння.** Інструменти працюють довше за ліміт однієї команди агента (у
Claude Code 2 хв за замовчуванням, максимум 10 хв): `qa-run` на типовому проєкті (10–50 сторінок,
більшість — CMS-записи кількох шаблонів) — до 30 хв (`budgetMinutes`, див. «Час прогону»), `lighthouse` ≈1 хв на
сторінку × форм-фактор × `runs`, `ios` ≈20–30 с на сторінку на пристрій. Тому кожен інструмент,
крім `record` і `manifest`, запускається **у фоні** засобом агента (Claude Code:
`run_in_background` — вивід він збирає сам, перенаправлення не потрібне). Людина в терміналі:
спершу `mkdir -p qa-out` (PowerShell: `New-Item -ItemType Directory -Force qa-out`), потім
macOS/Linux/Git Bash `nohup node "$S/qa-run.cjs" --out qa-out > qa-out/qa-run.log 2>&1 &`;
PowerShell `Start-Process -NoNewWindow -FilePath node -ArgumentList @("`"$S\qa-run.cjs`"", '--out', 'qa-out') -RedirectStandardOutput qa-out\qa-run.log -RedirectStandardError qa-out\qa-run.err.log`
(лапки навколо шляху — бо в імені користувача Windows бувають пробіли). Стан читається з
`qa-out/progress.json` і лога. **Важкі інструменти — по одному**: другий на тому
самому сайті не стартує (замок `qa-out/.qa-lock.json`) і пише, хто тримає замок.

**Відновлення.** Чекпоінтів немає, і їх не імітують. Інструмент, що впав чи був зупинений, записує
свої рядки як NOT RUN із причиною (а не мовчить) і **перезапускається цілком**, з тими самими
аргументами, у ту саму `qa-out`; якщо відповідь «тримає замок» — спершу дочекатися процесу, що
його тримає, а не запускати другий. Перервана сесія агента продовжує з того кроку, якого ще немає
в `qa-out/results-*.json` поточного `run.json`. Заборонено «рятувати» прогін власним скриптом,
частковим виводом чи звуженням обсягу (`--quick`, `--pages`, `--engines`, `--widths`): такий
манифест не порівнюваний з іншими. `--quick` — лише для налагодження `qa-target.json`.

### Час прогону — куди він іде і чому стільки

**Правило: 30 хв — верхня межа `qa-run`, не ціль** (`budgetMinutes`, типовий проєкт — 10–50
сторінок, більшість — CMS-записи кількох шаблонів). Довше — лише з причиною, і людина завжди бачить,
**на що** пішов час: `manifest.md` починається з таблиці `## Time`.

| Step | Time | Why this long (pages × widths × engines, items) | Share |
|---|---|---|---|
| рядок на кожен крок `qa-run` і на кожен інший інструмент цього прогону | хв / с | скільки завантажень, сторінок, ширин, рушіїв, фаз, «N at a time»; що зрізав бюджет | % від суми |

Під таблицею — підсумок проти бюджету і найбільші підкроки `qa-run` (busy-час: завантаження сторінок,
кожен вид взаємодій, прокрутка, STATIC, скріншоти, умовні очікування й скільки вони зекономили).
Джерело — `_timing` у кожному `results-*.json` (`startMs`, `endMs`, `totalMs`, `why`; у `qa-run` ще
`steps` і `busy`), у `manifest-meta.json → timing` і в шапці handoff (загальний час і два найдовші
кроки). Поточні кроки видно в `qa-out/progress.json → steps` ще під час прогону.

**Порядок кроків — за пріоритетом** (бюджет зрізає з кінця): статичний прохід Chromium → дешеві
перевірки всього сайту (лінки, robots / sitemap, заголовки, CSS, вага) → header sweep → взаємодії
Chromium → статичний прохід WebKit і Firefox → їхні взаємодії → iPad → Edge. Зрізане — ⚠️ NOT RUN
у кожному зачепленому рядку з причиною (RUN-04) і рядок `cut` у таблиці; тихих ✅ не буває.

**Що тримає час у межах** (кожне скорочення записане, жодне не мовчить):
- **шаблонна вибірка** з 11 сторінок: CMS-записи одного шаблону ділять верстку, хедер, бургер і
  форми, тож усі ширини, взаємодії й інші рушії йдуть на ≤3 сторінках шаблону; **кожна** сторінка
  все одно проходить контентний статичний прохід на 1440 і 360. Які шаблони, скільки сторінок і
  що вибрано — нотатки RUN-04 і `pages.json → groups`;
- **паралельні контексти**: статичний прохід — `concurrency`, фази взаємодій — `interactConcurrency`
  (типово 2). Результат той самий, що й по одній: записи в реєстр відтворюються в порядку плану;
  hover, дропдауни й навігація (спільне «вже бачене» між сторінками) ідуть у порядку плану; бургер
  чекає навігацію й дропдауни, touch — hover;
- **умовні очікування** замість фіксованих пауз (тогли, слайдери, hover, бургер, оверлеї, якорі,
  header sweep, кінець прокрутки): крок іде далі, щойно немає скінченних анімацій і переходів,
  скрипти не змінюють стилі / класи / вузли і стан елемента не змінювався третину паузи (бургер і
  оверлеї — половину). Стара пауза лишилась стелею, тож сторінка, що не заспокоюється, міряється
  як раніше;
- **WebKit / Firefox — на опорних тирах 1440 · 768 · 360**; проміжні тири нижче 768 — лише в
  Chromium, з нотаткою в RUN-04 і XB-01 (`"xbWidths": "all"` повертає їх);
- **без паузи між запитами на 127.0.0.1 / localhost / `--local`** (`throttleMs` 0; живий хостинг —
  400 мс, як і раніше);
- INT-02 не повторює після кожного тогла те, що було обрізане ще до кліку (база при завантаженні).

Свідомо **не** скорочується: вікна виявлення автоплею слайдера (3,5–7 с), вибірка «застряглих»
анімацій, затримки hover-intent у дропдаунах, крок фокуса Tab, форми й пікери дат.

Заміри (одна машина, 127.0.0.1): фікстура `npm test` (6 сторінок, лише Chromium) — 282 → ≈130 с на
прогін; `npm run perf` (40 сторінок, Chromium + WebKit + Firefox) — 76,5 → 11,4 хв, жоден вид знахідок
не втрачено (ті самі рядки 🔴, менше повторів того самого дефекту на сторінках одного шаблону).

## NOT RUN — що це і як закривається

`⚠️ not-run` означає: перевірка стосується сайту, але інструмент її не виконав або виконав
частково — і назвав причину й маршрут. Це **незавершена робота**, не «пройдено» і не «немає
предмета» (останнє — ⊘ n/a, його ставить сам інструмент за свіпом присутності, RUN-02).
**Прогін не завершений, поки в манифесті є ⚠️ not-run** (`manifest.cjs` тоді виходить з кодом 3 і
друкує `unfinished=N`). Кожен такий рядок:

1. **закривається інструментом** — виправити причину (встановити рушій, задати селектор чи
   рішення в `qa-target.json`, дати сесію) і перезапустити цей інструмент цілком; або
2. **маршрутизується** — `record.cjs --status routed --note "хто, на якій машині, коли"`; рядок
   іде в чекліст handoff; або
3. **закривається людиною з доказом** — `record.cjs --status pass|fail|ask … --covers-not-run`,
   коли людина перевірила саме ту частину, якої бракувало.

| NOT RUN | Що зробити |
|---|---|
| бургер / тогли / слайдер / дропдауни «є на сторінці, селектор нічого не знайшов» | задати `selectors.burger` / `dropdown` / `section` у `qa-target.json` і перезапустити `qa-run`; або `--status na`, якщо на сайті цього справді немає |
| FORM-06, A11Y-09 без `--form-errors` | спитати людину в діалозі; «так» → перезапуск із прапором; «ні» → `--status routed --note "QA: стан помилки вручну"` |
| WebKit / Firefox / Edge не стартував | `npm run browsers` (Linux — людина: `sudo env "PATH=$PATH" npm run browsers-deps`); Edge — людина ставить або маршрут |
| XB-02, XB-03, LAY-09 не на macOS | маршрут: Mac у команді, орендований Mac, хмара **реальних** пристроїв — `routed` з виконавцем |
| XB-05 (Chrome на Android) | емулятор Android Studio з образом Google APIs або пристрій по USB — інакше `routed` |
| RUN-06 доступ: пароль / basic-auth / SSO | людина зберігає сесію (`storageState`) або експортує `QA_HTTP_USER` / `QA_HTTP_PASS` у **своєму** терміналі; агент пароль не вводить ніколи |
| рішення не задане (`projectType`, `englishVariant`, `staging`, `credit`, `donor`, `analyticsIds`…) | спитати в діалозі → записати в `qa-target.json` → перезапустити інструмент |
| TEXT-02 мова без словника | словник додається **для всієї команди**: людина, що поширює скіл, робить `npm install -E @cspell/dict-<мова>` у `scripts/` (package.json і lock фіксують його для кожної машини) і роздає оновлений скіл; на одній машині «тихо» не ставити — інакше два прогони дадуть різні манифести. До того — `routed` носієві мови |
| PERF-01 сторінка без оцінки | перезапуск на вільній машині; сторінки, що й далі без даних, — `routed` (pagespeed.web.dev людиною) |
| WP-*/FORM-08/09 на не-WordPress | манифест ставить ⊘ сам за RUN-05; якщо детекція помилилась — `"platform"` у `qa-target.json` і перезапуск, ручний `na` не ставити |

## Аудит адмінки платформи (крок 7) — за платформою з RUN-05

**WordPress** (`wp-admin-audit.js`, лише читання):
1. Людина логіниться **адміністратором** у своїй вкладці; агент пароль не вводить.
2. Агент відкриває екран без блокування поста: блокова тема — `/wp-admin/site-editor.php`, інакше
   редактор сторінки, яку зараз ніхто не редагує. **Нічого не натискати**: ні «Take over», ні
   «Attempt block recovery», ні Save / Update. Іти без збереження.
3. `node "$S/wp-admin-cfg.cjs" --out qa-out` (з теки проєкту, після кроку 2) пише
   `qa-out/wp-admin.cfg.js` — `qa-target.json` + `pages` (`pages.json → all`) + `presence`
   (`results-qa-run.json → _presence`). Текст цього файлу **без змін** виконати у вкладці. Ніколи
   не складати `QA_WP_CFG` руками.
4. Виконати текст `<skill>/scripts/wp-admin-audit.js` у вкладці, опитувати `QA_WP.status()` до `done`.
5. Перенести `QA_WP.chunk(0…parts-1)` по черзі, без правок, у `qa-out/wp-admin.raw.json`;
   ніколи не передруковувати й не «лагодити» JSON руками.
6. `node "$S/record.cjs" --out qa-out --import qa-out/wp-admin.raw.json --tool wp-admin --len <QA_WP.len> --sum <QA_WP.sum>`
   — `record.cjs` відмовляє, якщо довжина чи хеш копії не збігаються (тоді перенести знову, звіряючи
   кожен шматок із `QA_WP.sums[i]`).

Ключі `QA_WP_CFG` (з `qa-target.json → wp`, потім `decisions`): `themeAuthor`, `productionDomain`,
`agencyEmailDomains[]`, `testAddresses[]`, `clientRecipients[]`, `requiredPlugins[]`, `cachePlugins[]`,
`imagePlugins[]`, `devMuPlugins[]`, `requireCachePlugin`, `requireImagePlugin`, `mailSubjectHasPage`,
`autoReply`, `maxAdmins`, `maxRenderedPages`, `throttleMs`. Без конфігу кожна залежна від рішення
підперевірка стає ❓, а не вгаданим 🔴.

**Webflow** (рядки з `tool: webflow` — WF-01, -04, -05, -06, -09, -10, -11; WF-07 — людина в Designer):
читати через підключення Webflow **лише на читання** (сторінки й custom code, зареєстровані
скрипти, колекції й записи, ассети з alt, `lastPublished` сайту), або людина в Designer. Результат
кожного рядка — `record.cjs --id WF-0x --status pass|fail|ask --note "…"`. Без підключення й без
людини — `routed`. Нічого не записується в проєкт під час прогону. FORM-08/09 на Webflow: Site
settings → Forms і Email Notifications **кожної** форми (override сильніший за сайтовий) — через
підключення, якщо воно це віддає, інакше людина → `record.cjs`.

**Інша платформа / статика:** WP-* і WF-* манифест ставить ⊘ сам. FORM-08/09 маршрутизуються
власнику бекенду форми (хост з `action` форми).

## Самоперевірка інструментів

`npm test` у `<skill>/scripts` проганяє інструменти на локальних фікстурах (лише 127.0.0.1, жодного
справжнього сайту). Запускати після встановлення, після оновлення скіла і після кожної правки
інструмента. Це перевірка скіла, а не сайту: у манифест сайту вона не потрапляє.

`npm run perf` — замір часу (не входить у `npm test`): генерує типовий проєкт на 40 сторінок (5 статичних
+ список журналу й робіт + 33 CMS-записи двох шаблонів зі спільними хедером, бургером, футером,
слайдером, FAQ і формою), віддає його з 127.0.0.1 і друкує таблицю `## Time` одного прогону
(`--engines`, `--items`, `--budget`, `--keep`).

`npm run release-check` (або `node release-check.cjs --deny <файл поза скілом>`) — перед тим як дати
скіл колегам: жодних бекапів, кешів, проєктних файлів, реальних домашніх шляхів, адрес і URL поза
example-доменами, валідний frontmatter `SKILL.md`; зі списком `--deny` — жодного імені клієнта,
проєкту, бренду чи людини. Сам список лежить **поза** скілом.

## Рішення, зафіксовані для всіх (practice rule, 2026-10-06)

Записані тут, щоб два прогони не трактували одне й те саме по-різному:

- **Дробові пікселі від `em`/`%`** (`padding: .1em` → 4.8px) — знахідка LAY-08. Виняток:
  `line-height` і невидимий UA-шрифт на іконкових кнопках без тексту.
- **Обов'язкові поля:** якщо поля змішані — позначка в кожного обов'язкового; якщо обов'язкові всі —
  одна видима примітка («All fields are required» або «* required»). Без жодної — 🔴 FORM-02.
- **Контраст над зображенням, градієнтом, `backdrop-filter` чи напівпрозорою підкладкою** ніколи не
  стає 🔴 автоматично: це ❓ зі скріншотом (A11Y-01). Хибний 🔴 одного з прогонів узявся саме звідси.
- **Edge (XB-04) і Chrome на Android (XB-05)** — обов'язкові рядки. Edge — справжній браузер через
  `qa-run`, якщо встановлений; «той самий рушій Chromium» не закриває рядок. «Поза обсягом» — лише
  ID із `decisions.outOfScope` з датою рішення дизайнера.
- **Тогли міряються розгорнутими.** Таби, акордеони, FAQ, панелі категорій, бургер із кожним
  підменю відкриваються по одному, і показаний вміст міряється знову (INT-01/02, NAV-03…05). Обидва
  попередні прогони пропустили баги саме через закриті стани.
- **Ховер — на всіх клікабельних елементах**, а не лише на кнопках (INT-05).
- **Lighthouse — лише послідовно й лише коли нічого іншого не запущено.** Паралельний прогін дав
  головній 43 замість 76. Інші джерела чисел (PSI, pagespeed.web.dev) — лише звірка, статус не змінюють.
- **Виміряне потрапляє в звіт.** Один прогін виміряв стрибок лого при відкритті бургера, але не
  записав його; тепер NAV-08 записує сам.
- **Хостинг з антиботом** («One moment, please…»): інструменти самі чекають, зменшують темп і
  позначають сторінку, яку не вдалося прочитати, як NOT RUN, а не як виміряну.
- **Аудит лише на читання.** Жоден інструмент не змінює сайт, CMS чи налаштування платформи;
  запити сторінки, крім GET/HEAD/OPTIONS, блокуються (окрім порожньої відправки з `--form-errors`).
